# Canary implementation plan

The hackathon training program is complete within its declared signal-description scope. Thirteen component categories passed. Both dated radiator-valve failures remain in the evidence. The root README and [architecture](architecture.md) describe the implemented system.

## Completed work

- Public data acquisition, pinned inventories, native TimeNet/TimeF preparation, and device/time separation.
- Separate Gemma-based OpenTSLM component training, validation selection, frozen evaluation, numerical controls, and checkpoint exports.
- Three saved real HDD cases with raw charts, exact model answers, and provenance.
- A synthetic 3D fleet with component inspection, timeline, illustrative rules, and a copilot.
- Public-project documentation, MIT licensing for original code, dependency setup, and local release verification.

## Release work

Preserve the verified local code on the release branch. Review remote changes independently before integration. The remote benchmark-inference experiment is not part of the saved-evidence demo.

Remove Entire integration and its dedicated records as requested after the hackathon. Preserve normal source history and model/evaluation archives. Do not install recording hooks during setup.

Prepare a tagged source release and keep the original experiment artifacts unchanged. Verify the final source commit, artifact hashes, CI, and anonymous downloads before claiming a completed public release. Repository visibility and release publication are separate external actions.

## Future research and product work

1. Add live model inference through an input contract that preserves channel meaning, cadence, normalization, and observed-window boundaries.
2. Evaluate descriptions against independent expert judgments and new untouched devices.
3. Establish fault outcomes, alert precision, false-alert burden, and useful warning lead time before claiming failure prediction.
4. Fit and evaluate calibrated risk only where outcome and follow-up support are adequate.
5. Validate maintenance decisions before adding operational recommendations.
6. Add authentication, deployment controls, and service monitoring before internet-facing application hosting.

## Rules for new training

Work alone unless the user explicitly changes that instruction. Explain and record every training run before launch, including diagnostics. Use disjoint devices and ordered time partitions where chronology exists. Preserve the sound studies' unknown-date limitation.

New runs require new directories, verified sources, validation-only checkpoint selection, and frozen test protocols. Preserve the failed experiments. Do not retrain a released run.

Paid runs require current rates and balance, an explicit budget, and a tested provider stop control. Historical voucher amounts and provider deadlines are not current authorization or configuration. See [reproduction](reproduction.md).
